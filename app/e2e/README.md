# 브라우저 시험 (e2e)

실제 브라우저(Chromium)로 앱을 조작하면서 폰(390px)과 PC(1280px) 화면에서 흐름을 확인해요. 단위 테스트(`npm test`)가 계산 로직을 지킨다면, 이 시험은 화면과 흐름을 지켜요.

```bash
npm install
npx playwright-core install chromium     # 처음 한 번. 이미 설치된 Chrome을 쓰려면 아래 CHROMIUM_PATH 사용
npm run e2e                              # 빌드 → 서버 → 모든 시험 → 요약
CHROMIUM_PATH="/path/to/chrome" npm run e2e
OUT_DIR=./e2e-out npm run e2e            # 스크린샷 저장 위치(기본: 시스템 임시 폴더)
```

| 시험 | 확인하는 것 |
|---|---|
| `wizard` | 새 여행 → 항공 → 숙소 → 일정 → 준비 → 예산 합계, 새로고침 후 유지, 이전 버전 데이터 호환 |
| `features` | 후보지 보관함, 불러오기 칩, 하루 경로 링크, 일정 가능 시간대·경고, 준비물 |
| `calendar` | 기간만큼의 캘린더(1주·2주·하루), 날짜 → 일정 이동, 고정 머리글, 입구 버튼, 뒤로가기 |
| `ledger` | 나라 선택, 환율(응답을 흉내 낸 것), 지출 기록·환산·수정·삭제, 계획 비용 불러오기, 국내·해외 차이 |
| `pwa` | 브라우저의 설치 가능성 검사, 아이콘, 오프라인, 설치 안내(이벤트는 직접 만들어 보냄), 아이폰 안내 |
| `viewer` | 단일 파일 버전을 `confirm()`·공유·클립보드·다운로드가 막힌 환경처럼 조작 |

## 알아 둘 점
- **환율 응답은 흉내 낸 것입니다.** `ledger`는 외부 환율 서비스를 호출하지 않고 브라우저에서 응답을 가로채 가짜 응답을 줍니다. 앱이 응답을 처리하는 방식만 확인하고, 실제 서비스의 응답 형식과 같은지는 확인하지 못해요. 인터넷이 되는 환경에서 실제 호출을 한 번 확인해 보세요(`src/lib/fx.ts`).
- **설치 이벤트도 흉내 낸 것입니다.** `pwa`의 `beforeinstallprompt`는 직접 만들어 보낸 이벤트예요. 실제 설치와 홈 화면 아이콘 모양은 실제 폰에서 확인해야 해요.
- 시험 시나리오가 의도한 동작 변화를 따라가지 못해서 실패하는 일이 있었어요(라벨 이름 변경, 국내 여행에 여권 추천 없음 등). 실패하면 앱이 깨진 건지 시험이 옛 동작을 기대하는 건지 먼저 가려 보세요.
- `vite preview`는 시작할 때의 파일 목록을 기억해서, 다시 빌드한 뒤에는 서버를 다시 띄워야 해요. `npm run e2e`는 매번 새로 띄워요. 직접 서버를 띄울 때는 JS 응답의 `content-type`이 `text/javascript`인지 확인하세요(`text/html`이면 대체 페이지가 오는 중이라 잘못된 서버예요).
